## 01 — PROBLEM

Telecom businesses need to identify customers who may leave so that retention actions can be prioritized. The engineering challenge is to turn customer-level tabular data into a reproducible prediction service rather than stopping at a notebook.

## 02 — WHY THIS APPROACH

The project treats the notebook model as the foundation of a larger system:

```text
CUSTOMER DATA
      ↓
DATA VALIDATION
      ↓
PREPROCESSING
      ↓
FEATURE ENGINEERING
      ↓
MODEL COMPARISON
      ↓
BEST MODEL
      ↓
FASTAPI
      ↓
WEB UI
      ↓
DOCKER
      ↓
DEPLOYMENT PATH
```

## 03 — DATA

Dataset: Telco Customer Churn.

The workflow covers missing-value handling, categorical encoding, scaling where required, train/test separation and exploratory analysis before model training.

## 04 — ARCHITECTURE

| LAYER | RESPONSIBILITY |
| --- | --- |
| DATA | Load and validate customer records |
| PREPROCESSING | Missing values, encoding and feature preparation |
| MODEL | Train and compare classification models |
| EVALUATION | Precision, recall, F1 and ROC-AUC |
| API | Expose prediction endpoint through FastAPI |
| UI | Collect customer inputs and show prediction |
| CONTAINER | Reproducible runtime through Docker |

## 05 — IMPLEMENTATION

The repository contains the training workflow, API layer, frontend and Docker configuration. The model artifact is generated by running the training pipeline rather than being committed as a binary output.

## 06 — MODEL

Models compared:

- Logistic Regression
- Random Forest
- XGBoost

The final model should be selected from measured validation results rather than from a predetermined preference.

## 07 — EVALUATION

The evaluation set includes:

`Accuracy` · `Precision` · `Recall` · `F1 Score` · `ROC-AUC`

For churn detection, recall and precision are interpreted alongside the business cost of false positives and false negatives.

## 08 — API / APPLICATION

FastAPI provides the serving layer. The UI sends customer features to the prediction endpoint and renders the result for an end user.

API documentation is available through FastAPI's `/docs` route when the project is run locally.

## 09 — DEPLOYMENT

The repository includes Docker packaging and can be connected to a free or low-cost container hosting platform. Azure is not required for the project architecture.

## 10 — RESULTS

Use the measured metrics generated by the training run here. Do not publish placeholder values. The portfolio intentionally avoids inventing performance numbers.

## 11 — ENGINEERING DECISIONS

1. Keep preprocessing reproducible.
2. Compare multiple baseline models rather than assuming one algorithm is sufficient.
3. Separate training from inference.
4. Serve the model behind a documented API.
5. Package the runtime so the application can be reproduced elsewhere.

## 12 — LIMITATIONS

The dataset represents one telecom churn scenario and may not generalize directly to another customer base. Model quality is also dependent on the feature definitions, class balance and decision threshold used during evaluation.
